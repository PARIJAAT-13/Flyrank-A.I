Ranking Content for Refresh Review with Observable Signals

A decision-support model that flags declining content for human review — no titles, URLs, or keywords used

Title & Abstract

Title: Ranking Content for Refresh Review with Observable Signals — A Decision-Support Approach

Abstract. Content platforms must decide which pages to review for refresh, but editorial bandwidth is finite. We build a ranked refresh-priority model for 30,000 anonymized content pages using only observable engagement signals (visibility, freshness, position, click-through rate, session depth). The label is trend_direction == "down" — a transparent, rule-based definition that makes the objective auditable. On a strict client-holdout split, a RandomForest model achieves 0.740 Precision@50 — roughly 3× the transparent rule baseline at 0.240 — and produces a 30,000-row ranked queue with 3,602 high-confidence rows ready for editorial review. The model is a decision-support aid, not an automatic publishing gate. All figures are directional and derived from a 30k-row teaching slice of a larger warehouse.

1. Introduction & Problem Statement

Large content libraries accumulate pages that lose engagement over time. A refresh workflow — updating stale titles, refreshing multimedia, or expanding thin content — can recover impressions and sessions. But with thousands of pages, editors need a principled way to decide which pages to review first.

Research question. Given a page's observable engagement signals, can we rank pages by their likelihood of being a refresh candidate, using only non-leaky features (i.e., features that would be available before the refresh decision is made)?

Decision it supports. A human reviewer should inspect the top of the ranked queue first. The model is a decision-support aid, not an automatic publishing gate. Every recommendation is paired with reason codes so an editor can understand why a page was flagged.

Why it matters. The transparent rule baseline catches only 24% of declining rows in the top 50 recommendations. The best model raises that to 74% — a 3× improvement on the same holdout split — without ever accessing a page's title, URL, or keyword text.

2. Data

Source and scope

  • Release: data/raw/content_refresh_anonymized.csv — a bundled anonymized starter slice
  • Size: 30,000 rows × 44 columns, 32 pseudonymized clients
  • Window: trailing 90-day activity totals (GSC + GA4 style metrics)
  • Public-safe: no client names, URLs, titles, keywords, or raw private queries

Label definition

The binary label is derived from the trend column: is_declining_label = (trend_direction == "down"). This yields 16,262 positive rows (54.2%). The trend columns themselves are never used as model features — they are leakage guards.

Feature set

After preprocessing, the models consume 52 columns:

  • 18 numeric features — log1p-transformed heavy-tailed counts (impressions, clicks, sessions), plus normalized rates and percentiles (CTR, scroll rate, engagement rate, avg position, search volume, competition, CPC)
  • 8 categorical features — one-hot encoded with an unknown level: content type, main intent, competition level, age tier, freshness tier, word count tier, impression tier, position tier

Exclusions

W05 baseline_score regression is excluded. That notebook uses the baseline as its own target, so MAE = 0 by construction. It is not a valid benchmark and is not used anywhere in this paper.

3. Methodology

Baseline score

The transparent rule baseline is a weighted sum of normalized, non-leaky components:

baseline_refresh_score = 0.40·visibility_score + 0.30·freshness_risk_score + 0.25·position_opportunity_score + 0.05·depth_gap_score

All components are percentile-rank or normalized values computed from observable signals. The baseline achieves Precision@50 = 0.240 and ROC AUC = 0.627 on the same holdout split.

Validation design

Client-holdout split: shuffle the 32 pseudonymized clients, hold out ~20% (~6–7 clients) as the test set, and train on the remainder. If client_holdout cannot be applied (e.g., insufficient clients), the pipeline falls back to a stratified row-holdout split. This measures intra-client generalization — how well the model performs on content from clients it has not seen during training.

  • Train rows: 27,675  |  Test rows: 2,325
  • Target positive rate: 0.542
  • Final score blend: 100 × (0.70 · best_model_probability + 0.30 · baseline_score_normalized), clipped to [0, 100]

Primary metric

Precision@50 — the proportion of true declining rows among the top 50 recommended items. This is the metric used to select the best model, because in a refresh workflow the reviewer can only act on a small number of high-priority items. Secondary metrics are ROC AUC and average precision.

Leakage checks

  • trend_direction and trend_pct never enter the feature set
  • content_id and client_id are used for grouping only
  • The label is computed after feature extraction, ensuring no temporal leakage

5. Limitations & Honest Framing

This work cannot claim the following:

  1. Sample size. This is a 30k-row teaching slice of a much larger warehouse. Precision figures are directional, not production-final.
  2. Temporal generalization. The client-holdout split measures intra-client generalization, not performance on future months. No temporal validation was performed.
  3. No causal claims. The model observes correlations in observable signals; it does not prove that the signals cause decline.
  4. Missingness. Categorical features are one-hot encoded with a single unknown level — some missingness patterns may silently encode content type.
  5. Baseline scope. The baseline is a transparent hand-written rule, not a market-beating system. The 3× improvement is measured against this specific rule on this specific slice.
  6. No titles/URLs/keywords. By design, the model uses only engagement signals. Adding textual or structural page content would require different data pipelines and separate validation.

Despite these limitations, the model provides a useful, auditable first pass for editorial review. The ranked queue narrows 30,000 rows to 3,602 high-confidence candidates — a 88% reduction in review load.

6. Ranked Recommendations

Action playbook — what a person should do first, with reasons:

  1. Inspect high-confidence rows first (final_refresh_score ≥ p80 = 63.6). These are the strongest model-decline signals with volume — 3,602 rows.
  2. Check refresh_and_review_ctr rows — declining with demand but low CTR on a visible page. Small edits may recover impressions; 6,654 rows in the queue.
  3. Review refresh_and_review_engagement rows — declining with demand and weak engagement metrics. 1,993 rows.
  4. expand_and_refresh rows are thin visible pages — consider adding content depth. Only 82 rows.
  5. monitor rows (low confidence) are not urgent; keep them on a periodic review cadence. 13,083 rows.

7. Reproducibility

The entire pipeline is deterministic under random_state=42 and is documented in the repository.

Canonical pipeline

  1. scripts/01_prepare_features.py — builds the feature vector from data/raw/content_refresh_anonymized.csv
  2. scripts/02_baseline_score.py — computes the transparent rule baseline
  3. scripts/03_train_model.py — trains all three models with client-holdout split
  4. scripts/04_evaluate_and_export.py — evaluates, ranks, and exports the queue
  5. scripts/05_build_pdf_report.py — generates the PDF report

Orchestrated via scripts/run_all.py. Re-running the pipeline from scratch reproduces all metrics exactly because every stochastic step uses random_state=42.

Committed artifacts

  • outputs/model_results.json — full metrics for all models and the baseline
  • outputs/summary.json — queue summary, confidence tiers, final score percentiles
  • outputs/refresh_queue.csv — the complete 30,000-row ranked queue
  • outputs/charts/*.svg — all five charts embedded in this paper
  • work/notebooks/capstone.ipynb — end-to-end notebook that documents each section
  • docs/index.html — this research paper

How to verify: clone the repository and run python scripts/run_all.py. The output metrics should match the tables in Section 4 exactly. The notebook can be executed with jupyter nbconvert --execute --to notebook work/notebooks/capstone.ipynb.
